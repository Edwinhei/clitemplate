## 已确立的工程约束(不要破坏)

| 约束 | 落在哪 | 防什么 |
|---|---|---|
| **契约优先** —— 先改契约再改实现;删掉 `apps/api` 前端要能编译 | `contracts/README.md` | 前端依赖实现而非契约 |
| **只用可擦除语法** —— `erasableSyntaxOnly: true` | `tsconfig.base.json` | 被迫加构建步骤 |
| **`types` 按包声明** —— base 不写 `types` | 各包 tsconfig | 同构包偷偷绑死 Node |
| **按能力域分目录** —— `packages/<域>/<包>/` | 目录结构 | 改一个需求跳三个目录 |
| **配置属于 app** —— `cordis.yml` 在 `apps/cli/`,从包内路径解析 | `apps/cli/` | 仓库根目录暗示"只有一个应用" |
| **包名即分层** | 命名规范(见下) | 可替换性看不见 |
| **有 config 的插件必须导出 `Config` schema** | 各插件 src/index.ts | 配置写错时症状离根因三跳 |
| **可观测性设施由宿主挂载,不进配置树** | `apps/cli/src/boot.ts` | 漏掉启动最早期的日志 |
| **只有宿主能直接读 `process.env`** | `@ctl/env-launch` | 插件绑死 Node、依赖隐形 |
| **引导期和配置树共用同一份环境组装逻辑** | `loadLaunchEnv()` | 两边看到不一样的环境 |
| **清理只写 `ctx.effect`,不用 `apply` 的返回值** | 各插件 | 标准写法下 `apply` 的返回值**被静默丢弃** |
| **审计前先 `await ctx.loader.await()`** | `boot.ts` | `create()` 不等被唤醒的下游,审计会误判 |
| **基线声明全部候选,patch 只管开关** | `cordis.yml` + `patches/` | patch **改不了 `name`** |
| **版本号只写一处** —— 一律走 catalog 协议 | `pnpm-workspace.yaml` | 版本分叉 → 两份实体，静默翻车 |
| **框架本体不许开具名目录** | `verify-catalog` 的 `SINGLETON` | 两份 cordis 共存，`instanceof` 静默失效 |
| **宿主用 dependency，插件用 peer** | 各包 package.json | 框架被装成两份 |
| **`exports` 是库的属性，`bin` 是应用的属性** | 各包 package.json | app 和 package 形态混淆 |

## 已踩的坑(都记在根 README 的「已知陷阱」)

1. **`cordis.yml` 顶层必须是数组** —— 全部注释掉 = `null`,报
   `TypeError: config file must be a top-level array`;要空就写 `[]`
2. **条目 `id` 必须唯一** —— `duplicate loader entry id: xxx`
3. **读 Cordis 错误三步** —— 看动词(`import`/`apply`)→ 看括号里的 `id` → 看最底下 `[cause]`
4. **`--import tsx` 依赖 cwd** —— 仓库外调用会 `Cannot find package 'tsx'`;裸 node 无此问题
5. **`@types/node` 要显式装** —— tsconfig 写了 `types: ["node"]` 但没装包,
   报错离根因有两跳(「找不到 process」→ 其实是「@types/node 没装」)
6. **叶子包要声明自己的依赖** —— pnpm 严格 node_modules 不提升
7. **`node-addon-require-builtin` 是 loader 的必需拼图** —— 它是 loader 的
   **可选 peer**，缺了不报错只静默降级：裸包名会从 loader 自己所在目录解析，
   而不是从 `ctx.baseUrl`（配置文件所在目录）。症状是明明装好了却
   `Cannot find package '@ctl/xxx'`。装在 `apps/cli`（谁启动 loader 谁喂 peer）
8. **`packageManager` 由 corepack 强制执行** —— 写错版本号会触发
   `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR`（要求清空 node_modules 重装）。
   本仓库基线 `pnpm@10.17.0`，升级必须是一次有意识的动作
10. **`PENDING` 不是阻塞** —— `inject` 依赖缺失时 `ctx.plugin()` **立刻返回**，
    fiber 停在 `PENDING`(=0)。它不占 event loop 任何资源,所以进程照常退出、
    退出码 0、什么都不打印。**这是「插件没反应」的成因**,不是 bug 是设计
    (依赖晚点到就会自动激活,实测 300ms 后挂上提供方 → 消费方自己变 ACTIVE)
9. **参数属性 `constructor(ctx, private config: C)` 不可擦除** —— 违反
   `erasableSyntaxOnly`，裸 node 报 `TypeScript parameter property is not
   supported in strip-only mode`。写成普通字段 + 普通参数。`pnpm typecheck` 能提前拦住

### 依赖三分法(结论)

判据不是"何时用",是 **"消费者装了我之后,跑我的代码时缺了它会不会炸"**。

```
消费者运行时不需要        → devDependencies（工具链 / 纯类型 / peer 的本地替身）
需要，且可以有两份        → dependencies
需要，且必须全场唯一      → peerDependencies + devDependencies
需要，但装不上也不该中断  → optionalDependencies
```

同一个 cordis：`apps/cli` 是 `dependency`（宿主，真的装），`packages/*` 是 `peer`（插件，用宿主那份）。

## 步骤 4 已完成:启动审计

### 解决什么

Cordis 头号坑「插件没反应」:`inject` 的服务永远不出现时,fiber 停在 `PENDING`,
**进程正常退出、退出码 0、零输出**。功能悄悄少一块,没人知道。

### 做法

新增 `apps/cli/src/audit.ts`,在 `loader.create()` **之后**巡场一遍(位置关键:
早于结算会把「还没轮到加载」误判成「永远等不到」)。

两关:

| 关 | 判据 | 说明 |
|---|---|---|
| 一 | `entry.fiber === undefined && !entry.disabled` | 模块压根没加载 |
| 二 | `fiber.state !== ACTIVE` | 加载了但没启动 |

第二关按状态分流:`FAILED` → `await fiber.await()` 取出原始错误;
`PENDING` → `Object.keys(fiber.inject)` 减去 `fiber.ctx.get(s) !== undefined`
= **它在等谁**。

`FiberState` 是 const enum,`erasableSyntaxOnly` 下不能当值用,
所以做值镜像 `const FIBER_ACTIVE = 2 as FiberState.ACTIVE`(harness 同款写法)。

### 故障归属边界(实测确认)

| 故障 | 谁来管 |
|---|---|
| 模块找不到(`import` 阶段) | **loader 自己**,当场炸 |
| `apply` 里抛错(`apply` 阶段) | **loader 自己**,当场炸,审计根本执行不到 |
| **依赖等不到(`PENDING`)** | **只有审计能抓** |

### 验收结果

```
实验 1 正常情况         → 不误报,三行输出,exit 0
实验 2 注释掉提供方     → Error: ctl: 1 个插件没能激活
                            @ctl/tool-notify
                              等待服务：notify
                          exit 1
实验 3 apply 抛错       → loader 先炸,审计未执行(边界符合预期)
```

## 步骤 5 已完成:宿主事实作为服务

### 解决什么

插件直接写 `process.env.XXX` 会同时坏掉三样东西:

1. **绑死 Node** —— 同构包再也跑不了浏览器 / Worker / Deno
2. **依赖隐形** —— `inject` 那行看不出它还要一个环境变量,生产上少配了才发现
3. **测不了、换不了** —— 想换测试值只能改全局;想换远程配置源只能改代码

解法和 notify 一模一样:**把「宿主事实」也做成一块招牌**。

### 抄自 harness `dsh-launch-environment` 的两个设计

**① 快照,不是实时读。** 构造时对 `process.env` 拍一次照,之后只看照片。
`process.env` 是可变全局,任何第三方库都能中途改它 —— 实时读意味着同一个插件
在不同时刻可能拿到不同的值,而且查不出是谁改的。

**② 值带来源,不只是字符串。**

```ts
export interface EnvValue { value: string; source: string }
getFrom(name: string, sources: string[]): EnvValue | undefined
```

harness 原话:**"Omitting a layer is a refusal, not a demotion."**
(不列出某一层是拒绝,不是降级)—— `getFrom('API_KEY', ['process'])` 是明确宣布
「只接受 shell 传进来的」,将来优先级怎么调整都漏不进来。
现在只有一层,但接口先按分层设计,步骤 9 的 patch 分层会直接用上。

### 验收结果

```
① 默认                              → 收件人 ops   来自 (默认值)
② CTL_NOTIFY_TO=alice               → 收件人 alice 来自 process
③ 换成 env-static + 仍带 alice      → 收件人 bob   来自 static   ← alice 被彻底无视
④ tool-notify 里写 process.cwd()    → TS2580 Cannot find name 'process'  ← 门禁挡住
```

③ 是核心:**环境变量设了却完全不起作用**,因为这次挂 env 招牌的店压根不读
`process.env`。而 `tool-notify` 一个字没改。

### 消费方的变化

```diff
-export const inject = ['notify']
+export const inject = ['notify', 'env']

-  await ctx.notify.send({ to: 'ops', … })
+  const found = ctx.env.get('CTL_NOTIFY_TO')
+  await ctx.notify.send({ to: found?.value ?? 'ops', … })
```

依赖从「藏在函数体里的 process.env」变成「写在 inject 那一行、一眼可见」。

## 步骤 6 已完成:配置 schema

### ⚠️ 更正一条旧结论

此前说过「Cordis 官方要求用 Schemastery,不要纠结」—— **在 cordis 4.0.1 上这是错的**。

```js
// cordis/lib/index.js resolveConfig
const result = runtime.Config["~standard"].validate(config)
```
```ts
// registry.d.ts
Config?: StandardSchemaV1<any, T>
```

`~standard` 是 **Standard Schema** 规范。**任何实现它的库都行** ——
zod 3.24+/4、valibot、arktype、schemastery。实测 schemastery 和 zod v4 均可用,
报错信息各有格式但都能被 cordis 正确渲染。

**模板选 schemastery 的真实理由是:它双向。** schema 不只能校验,还能反过来
渲染成配置表单 —— harness 的 Web UI 自动生成插件配置界面靠的就是这个。
zod 只能单向。**确定不做配置 UI 的项目,用 zod 完全没问题。**

### 没有 schema 的代价(实测)

cordis.yml 里把 `path` 打成 `paht`:

```
Error: ctl: 1 个插件没能激活
  @ctl/tool-notify
    fiber 状态异常：1
```

报的是 **tool-notify**,而改错的是 **notify-file** 的配置。断链:

```
paht → config.path = undefined
     → FileNotify 构造函数里 super(ctx,'notify') 先跑,招牌挂上了
     → 下一行 new URL(undefined, baseUrl) 抛错,招牌又被摘走
     → 这中间 tool-notify 已被唤醒、apply 跑到一半
     → 审计跑过来时它卡在 LOADING(1)
```

**根因和症状隔三跳,中间还夹一次「招牌挂上又被摘走」的竞态。**

### 有 schema 之后

```
failed to apply loader entry notify (@ctl/notify-file): invalid config:
  - $.path missing required value (at path)
```

哪个条目 / 哪个包 / 哪个字段 / 什么问题,一行说完。

**关键在时机:校验发生在 `apply` 之前。** 所以插件代码里可以直接写
`config.path`,不必做任何防御性判断 —— 拿到手时已被保证合法。

### 写法

```ts
export interface Config { path: string }

/** 名字必须叫 Config（Cordis 认这个名字），和 interface 同名做声明合并 */
export const Config: Schema<Config> = Schema.object({
  path: Schema.string().required().description('…'),
})
```

`interface Config` 在类型空间、`const Config` 在值空间,TS 声明合并允许同名。
这是 cordis 生态的标准写法。

**schemastery 进 `dependencies` 而非 peer** —— 它不做 `instanceof` 身份判断,
两份共存不会翻车。判据表第二问的直接应用。

### 验收结果


## 步骤 7 已完成:日志

### 意外一:契约是 Cordis 自带的

原计划建 `@ctl/logger` 契约包,扒源码发现不需要:

```ts
// cordis/lib/types/context.d.ts
logger: LoggerService
// cordis/lib/types/logger.d.ts
export interface Exporter { levels?: Record<string, number>; export(message: Message): void }
```

```
契约   →  Cordis 内置的 LoggerService + Exporter    ← 不用自己写
提供方 →  实现 Exporter 的插件(console / file / 远程)
消费方 →  各插件里的 ctx.logger.info(...)
```

**契约不一定要自己写,框架给了就直接用。**

### 意外二:sink 必须由宿主挂载

链条(全部实测):

1. `ctx.logger` 永远可用,但**没有 sink 时消息被静默丢弃**
2. 消息进了 `ctx.logger.buffer`(保留最近 1000 条),但**不会回放**给后来的 sink
3. 配置树条目是 `Promise.allSettled` **并发** apply 的 ——
   `cordis.yml` 里写在第一行也保证不了先跑完
4. 想 `inject: ['logger']` 等它?**永远 PENDING** ——
   logger 是 Context 内置属性,不在 registry 里:
   `ctx.get('logger')` 和 `ctx.get('logger', false)` 都返回 `undefined`

**证据**:文件 sink 挂在 cordis.yml 时,`ctl.log` 里最小的 `sn` 是 3;
而 `ctx.logger.buffer` 里明明有 `sn=1 name=hello`。挪进 `boot.ts` 后 `sn=1` 就有了。

所以:

```ts
await ctx.plugin(Loader)
await ctx.plugin(ConsoleExporter, { showTime: 'hh:mm:ss' })   // ★ 必须在 create 之前
const logFile = process.env.CTL_LOG_FILE                       // 宿主才能直接读 env
if (logFile) await ctx.plugin(FileExporter, { path: logFile, levels: {} })
await ctx.loader.create({ … })
```

> harness 的 `boot()` 为此留了 `prepare` 钩子:
> "run after Loader installation and **before any config-tree entry mounts**"。

### 三个细节

**① 级别数字是「啰嗦程度」不是「严重程度」**

```
ERROR=0（永远显示） INFO=1（默认阈值） WARN=2（默认看不见！） DEBUG=3
```

**② logger 名字自动取自插件 `name`**;但在 `Service` 内部是从**类名**推导的
(`class ConsoleNotify` → `console-notify`,和包名 `notify-console` 对不上),
所以显式写 `this.ctx.logger('notify-console')`。

**③ sink 可叠加** —— 每条消息送到所有已注册 sink。不是「换 exporter」是「再加一个」。
(`ctx.logger.exporters` 里本来就有一个内置的 buffer sink,所以 size 总是比你挂的多 1。)

### `@ctl/logger-file`

JSON Lines,每条同时存结构化 `args`(机器可读)和渲染后的 `msg`(人可读,
用 `Logger.format(this, message)` 解 printf 占位符)。

**用 `appendFileSync`** 是有意识的取舍:CLI 可能在异步写落盘前就退出。
长驻服务该换成带 flush 的异步队列,代价是要处理退出收尾。

### 自己踩的坑

编辑 `cordis.yml` 时留了一条活着的 `logger-file` 条目没删,导致 FileExporter
被挂载两次 —— 表现是**每条日志在文件里出现两次**,以及「没设环境变量却还是
生成了 ctl.log」。**两个 sink 指向同一个文件 = 每条写两遍。**
排查靠的是 `exporters.size` 和 `sn` 字段。

**② 动态加载怎么发生** —— 实测两种:

```
  → hmr reload plugin at src/plugins/hello.ts
  → hello 插件启动了 ★改过了★

改 cordis.yml，把 notify-console 换成 notify-file
  → file-notify 已写入 .../notify.log      ← 提供方【活着换掉了】，消费方重新跑
```

**③ effect 的复原单第一次成为刚需** —— 见下面那个坑。

### ⚠️ 最重要的发现:`export function apply` 的返回值被静默丢弃

**初次归因错了**(以为是 HMR 不跑),真实变量是**插件的写法**。

cordis 调用插件前先判断(`lib/index.js:57`):

```js
function isConstructor(func) {
  if (!func.prototype) return false   // 箭头函数 / 对象简写方法：无 prototype
  return true                          // function 声明：有 prototype
}
```

然后分两条路(`:1066`):

```js
if (isConstructor(runtime.callback)) {
  const instance = new runtime.callback(this.ctx, this.config)
  return instance?.[symbols.init]?.()          // ← 返回值被丢弃
} else return runtime.callback(this.ctx, this.config)   // ← 返回值会被 collect(:1142)
```

**四种写法两种结果**(实测):

```
export function apply(c){}      prototype 存在 → 当构造函数 → 返回值丢弃 ✘
{ apply: function(c){} }        prototype 存在 → 同上                    ✘
{ apply(c){} }   简写方法        无 prototype   → 正常调用 → 收集         ✔
{ apply: (c)=>{} } 箭头函数      无 prototype   → 同上                    ✔
```

**cordis 生态的标准写法就是 `export function apply(ctx)`** ——
所以在我们所有插件里,`apply` 的返回值**永远不会成为复原单**,
不管走哪条卸载路径。不是「HMR 时不跑」,是「根本没被登记过」,
而且完全静默:无警告、无报错。

这就是 cordis 系列里那句「effect 是唯一的生命周期挂点」的**机制层面答案**:
不是建议,是标准写法下**没有第二个选择**。

顺带:`new apply(ctx, config)` 意味着 `apply` 是被 `new` 调用的,
函数体里 `this` 是个新对象而不是 `undefined`。插件里别用 `this`。

另外单独验过:`ctx.on('dispose', …)` 在任何路径下都**不触发**。

### 接线是宿主的活

两处都得宿主自己接:

**a. HMR 的 peer 服务** —— `Hmr.inject = ['loader', 'timer']`。
不挂 `cordis-plugin-timer`,HMR 就永远 PENDING(会被启动审计抓到)。

**b. cordis.yml 本身不在监视范围内** —— HMR 主监视器只认 `root` 下的**模块**,
YAML 不是模块。要用 `hmr.registerConfig(filename, refresh)` 单独挂精确路径。
而 `cordis-plugin-include` **不会自己接**(源码里没有任何 hmr 引用)。

Include 实例就是那条 entry 的 `subtree`,它有公开的 `refresh()`:
「重读文件,内容变了就事务性地刷新子条目」。

```ts
const includeId = await ctx.loader.create({ name: '…include', config: { path } })
for (const entry of ctx.loader.entries()) {
  if (entry.options.id !== includeId) continue
  const tree = entry.subtree as { refresh?: () => Promise<void> } | undefined
  if (typeof tree?.refresh === 'function') {
    await ctx.hmr.registerConfig(configPath, () => tree.refresh!())
  }
  break
}
```

### 为什么走显式开关而不是配置项

`CTL_WATCH=1` / `pnpm ctl:watch`。理由:**这是运行形态的切换,不是普通配置。**
HMR 一装上进程就不会自己退出了 —— 一次性 CLI 默认不该这样,
不然每敲一次命令都要 Ctrl+C。

三种形态,同一个内核:

```
一次性 CLI（默认）  boot → 干活 → event loop 空 → 退出 0
watch 模式          boot → HMR 持有 watcher → 一直活着
长驻服务（将来）    boot → 某插件 listen(3000) → 一直活着
```

### 遗留

**watch 模式下审计只覆盖首次结算。** 热重载后新出现的 PENDING 不会被抓 ——
`assertEntriesActivated` 是一次性的。要覆盖得监听 `internal/status` 事件,
留给以后。

## 步骤 9 已完成:patch 分层 + dump-config

### patch 的真实语义(全部实测)

| 字段 | 语义 |
|---|---|
| `id` | **定位**,必填 |
| `name` | **断言** —— 写了就必须和基线一致,不一致整条 patch 跳过并警告。**改不了 name** |
| `config` | **整体替换**,不是合并。`{a:1,b:2}` 打 `{b:99}` 的结果是 `{b:99}` |
| `disabled` | 开关。`false` 能把基线里关掉的重新打开 |
| `insert` | 往 **group** 条目里追加(目标不是 group 会警告跳过) |

- 多条 patch 依次执行,后面的能命中前面 `insert` 进来的条目
- 匹配不到只警告并跳过,**不让启动失败**
- 原始数据永不被修改,返回的是脱离的副本

### 由此推导出的组织方式

**`name` 改不了** → 「换实现」不能靠 patch 改 name,只能:

> **基线 `cordis.yml` 声明全部候选(备选项 `disabled: true`),
> patch 只负责开关。**

额外好处:一眼看得出这个 app 到底可能装哪些东西,而不是散在若干 patch 文件里等你拼。
而且**没人能靠 patch 偷偷塞进一个基线里没声明过的插件**。

### 文件布局

```
apps/cli/
├── cordis.yml            基线:全部候选
└── patches/
    ├── prod.yml          通知落盘（notify → notify-file）
    └── test.yml          环境值写死（env → env-static），输出可重复
```

### `--dump-config`

关键不在「能打印」,在**它和真正启动走同一个 `applyEntryPatches`**。
include 的官方注释:这个函数被 mounting 和离线 dump 共用,
「**所以 dump 永远不会和真正启动的东西脱节**」。

```bash
pnpm ctl --dump-config                      # 基线
CTL_PROFILE=prod pnpm ctl --dump-config     # 叠加后的最终组合
diff <(pnpm ctl:dump) <(CTL_PROFILE=prod pnpm ctl:dump)
```

解析要用 include 导出的 `entryListSchema`(js-yaml 必须 `^4.1.0` 同大版本),
否则 `!!js` 表达式节点解析不出来 —— 那个 tag 名就叫 `!!js`(`tag:yaml.org,2002:js`)。

### ⚠️ 顺带修掉一个真 bug:审计跑太早

切到 notify-file 之后,审计**确定性地**报
`@ctl/tool-notify fiber 状态异常：1`(LOADING),但配置完全正确。

量时序发现:

```
+0ms    notify=2  tool-notify=1     ← provider 已激活，consumer 还在 apply 中
+11ms   全部 =2
```

**`loader.create()` 只保证「这条 entry 挂上了」,不保证被它唤醒的下游也跑完了。**

修法:审计前先调 `EntryTree` 的公开方法 —— 语义是「等到这棵树没有任何
进行中的导入或生命周期任务」,而且 `entries()` 递归进子树:

```ts
await ctx.loader.await()
await assertEntriesActivated(ctx, 'ctl')
```

回归验证:审计仍能抓到真 PENDING(注释掉提供方 → `等待服务：notify`)。

> 这个 bug 从步骤 4 起就潜伏着,只在「provider 唤醒 consumer」这条路径上暴露。
> notify-console 恰好快到能赶上,notify-file 慢一点就现形了 ——
> **典型的时序竞态:不是「有没有」,是「够不够快」。**

## 步骤 10 已完成:门禁脚本

### 这是「三层执行力」的最后一层


### 六道门禁

| 门禁 | 守什么 | 拦住的真实事故 |
|---|---|---|
| `package-invariants` | 包的形态与它在依赖图里的位置一致 | app 长出 `exports`、能力包长出 `bin`；`exports` 漏 `"./package.json"` |
| `dependency-layering` | 宿主用 dependency，插件用 peer;peer 必须配一份 dev | 框架被装成两份,`instanceof` 静默翻车 |
| `catalog` | 外部依赖一律 `catalog:` | 版本分叉 —— **peer 管不了这件事**(实测:pnpm 一句警告都没有,直接另装一份) |
| `runtime-closure` | `cordis.yml` 与 `patches/` 引用的包宿主都已声明 | **第一天撞的那个坑**;harness 有同名门禁 |
| `env-access` | 只有宿主能直接读 `process.env` | 插件绑死 Node、依赖隐形 |
| `effect-cleanup` | `apply` 不返回复原单 | 返回值被**静默丢弃**,热重载下泄漏句柄 |

### 关键实现决定

**① 不读 `pnpm-workspace.yaml` 的 glob** —— 门禁检查的是**约定的目录结构**
(`apps/*` 和 `packages/<域>/*`)。配置被改坏了,门禁反而更该报警。

**② 一次报全部,不是修一个跑一次** —— `verify.ts` 跑完所有门禁再汇总退出。

**③ 报错必须带修复建议** —— 每条违规都有 `fix`。门禁的价值不在「拦住」,
在「拦住之后让人知道怎么办」。

**④ 注释要挖空再检查,且保留行号** —— `env-access` 第一次跑就误报了:
`tool-notify` 的一句注释里提到了 `process.env`。
用等长空白替换注释内容,行号才不会错位。

### ⭐ 绿灯本身不能说明什么

**一道从不失败的门禁等于没有。** 六道门禁全部做了下毒测试:

```
① 删掉包的 description          → ✅ 抓到
② exports 去掉 "./package.json" → ✅ 抓到
③ 能力包的 cordis 改成 dependency → ✅ 抓到
④ 写死一个版本号                 → ✅ 抓到
⑤ cordis.yml 引用未声明的包      → ✅ 抓到
⑥ patch 里引用未声明的包         → ✅ 抓到（且报错指向 patches/prod.yml 而非 cordis.yml）
⑦ 插件里偷读 process.env        → ✅ 抓到（精确到行号）
⑧ apply 里 return 一个函数       → ✅ 抓到
```

**新增门禁时必须配一个下毒测试** —— 否则你不知道它到底在不在干活。

## 补记:catalog 的两个易混点(实测)

### ① `catalog` 和 `catalogs` 分属两套语法

```
pnpm-workspace.yaml 里 = 【配置字段名】
  catalog:      装「默认目录」
  catalogs:     装「一堆具名目录」→ 所以是复数

package.json 里 = 【依赖协议】，和 workspace: / npm: / file: 同类
  "catalog:"        默认目录
  "catalog:cli"     名叫 cli 的目录      → 协议名永远单数
```

实测:写成 `"catalogs:cli"` 报
`ERR_PNPM_SPEC_NOT_SUPPORTED_BY_ANY_RESOLVER`。
**复数只出现在「装东西的容器」那一侧。**

另外具名目录必须是**独立顶层键**。写成这样会报
`Invalid catalog entry for cli. Expected string, but found: object`:

```yaml
catalog:
  is-odd: '3.0.1'
  cli:                    # ❌ 嵌在 catalog 里 → pnpm 把 cli 当成包名
    is-odd: '2.0.0'
```

（`"catalog: cli"` 带空格能用,pnpm 会 trim。但别指望这种宽容。）

### ② 「版本号只写一处」≠「全仓库只准一个版本」

这两件事我一开始在门禁里混了,导致 `catalog:legacy` 被误判成硬版本。

不同 app 对同一个库依赖不同大版本是**正常工程现实**(web 用 react 19、
marketing 的旧站停在 18)。具名目录就是为此而生 —— **版本号依然只写在
`pnpm-workspace.yaml` 里,只是分了组。**

门禁该拦的是「散落在各 package.json 里的硬版本」,不是「有几个版本」。

### ③ 但框架本体是例外

实测两份 cordis 共存(`4.0.1` vs `4.0.1-rc.1`):

```
❌ 两份 Service / Context 类不是同一个
❌ 服务实例在宿主眼里不是 Service（instanceof false）
❌ 用另一份 cordis 建的 ctx 拿不到已挂的服务（undefined）
✅ 但基本调用居然还能走通        ← 最危险的地方
```

**它不会当场崩。** cordis 用 `Symbol.for` 注册服务、`Service` 自定义了
`hasInstance`,所以大部分路径侥幸能跑。只要有一处代码依赖真正的类身份,
就会拿到 `false` 或 `undefined` —— **而且没有任何报错。**

比直接崩坏得多:直接崩当场就修了,现在是「跑得好好的,某个分支下悄悄不对」。

**已写进门禁**:`verify-catalog` 的 `SINGLETON` 名单里的包出现在具名目录里 → 报错。

### ④ `catalogMode` 能消掉维护成本

```yaml
catalogMode: strict
```

之后 `pnpm add X` 会**自动**把 `"catalog:"` 写进 package.json、把版本号写进
`pnpm-workspace.yaml`,一步都不用多走。

⚠️ 但装冲突版本时会报 `ERROR Invalid Version: ^3.0.1` —— 报错信息毫无帮助,
它想说的是「catalog 里已经有了,冲突」。这时候手工建具名目录即可。
(`strict` 和 `prefer` 两个模式都这样。我们暂时没启用,因为这个粗糙边缘
比自动入库的收益更容易让人困惑。)
